# Dealify: public-app approval research — November 2026

Researched November 17, 2026 (Toronto; some live source pages show November 18 UTC). Scope: official Shopify requirements and supported architecture for a free first release. This is research and a proposed evidence plan, not Shopify approval, a fresh completed code audit, or proof of a production checkout. Shopify still performs its own review, including live behavior and listing content that local self-review cannot establish. [Review preparation](https://shopify.dev/docs/apps/launch/app-store-review/pass-app-review)

Repository context: `7356f3a394cd7b0f5113b541bfbbfcfc028e4413`, the existing launch assessment, `AGENTS.md`, `docs/PLAN.md`, `docs/SPEC.md`, `.env.example`, and the server were inspected as the baseline. Other agents are changing the repository concurrently; the evidence column below specifies what must be demonstrated, not that these changes already exist. Baseline: one configured Shopify store/token, Supabase owner login, a complete storefront theme, Backboard conversations/memory, native basic discount codes and mint-time KPI rows. [Baseline source](https://github.com/Maristanez/dealify/tree/7356f3a394cd7b0f5113b541bfbbfcfc028e4413)

## Recommended release shape

**Recommendation:** ship an embedded merchant Console, a theme app embed for the shopper chat, per-shop server and database isolation, and Shopify-hosted invoice checkout for ordinary one-time, variant-backed products. Keep the first release genuinely free. Launch a small pilot through public distribution after review, optionally using limited listing visibility. Keep subscription products, transformed bundles, cross-currency negotiation, voice retention and persistent cross-visit shopper memory outside the initial supported scope until each has explicit verification.

This recommendation combines documented surfaces: theme app embeds specifically support floating chat, draft orders support chat sales and invoice checkout, and public distribution supports multiple unrelated merchant stores. It is an implementation choice, not a promise of approval. [App embeds](https://shopify.dev/docs/apps/build/online-store/theme-app-extensions/configuration), [Draft orders](https://shopify.dev/docs/api/admin-graphql/latest/mutations/draftOrderCreate), [Distribution](https://shopify.dev/docs/apps/launch/distribution)

## Current changes that affect this project

- **Expiring tokens are mandatory for new public apps.** Existing public apps face delisting/new-install blocking on January 1, 2027, a merchant warning January 15, and rejection of non-expiring-token API requests April 1. A new app should request expiring offline tokens from its first install, store expiry/refresh state and rotate reliably. Application-only tokens signed with a client assertion are another expiring-token route. [Migration requirements](https://shopify.dev/docs/apps/build/authentication-authorization/migrate-to-expiring-offline-access-tokens)
- **The repository's `2026-01` default is too close to retirement for submission.** Shopify lists January 16, 2027, 15:00 UTC as its end of accessibility; `2026-10` is latest stable. Submission guidance excludes APIs due to deprecate within 90 days. Recommendation: explicitly target `2026-10`, validate every operation, and align webhook/extension versions. [Version schedule](https://shopify.dev/docs/api/usage/versioning), [Submission guidance](https://shopify.dev/docs/apps/launch/shopify-app-store/best-practices)
- **Client credentials are not universally restricted to owned stores anymore.** Plain client-secret grants remain organization-limited. Public apps can use private-key-signed client assertions for stores that have installed and authorized them. That does not supply the missing merchant installation, shop binding or admin authentication. [Authentication approaches](https://shopify.dev/docs/apps/build/authentication-authorization)
- **Custom distribution is not a reversible public-app pilot setting.** Distribution choice cannot later be changed. External-store custom-app installs require an IP allowlist from November 20, 2026; previously installed external custom apps need one from January 1, 2027. [Distribution selection](https://shopify.dev/docs/apps/launch/distribution/select-distribution-method)
- **AI processing needs an actual data-use policy.** Shopify's 2026 clarification restricts development/training use of merchant/customer data, including derived and aggregated data, without the required consent. Backboard memory being disabled is not evidence that provider training, logs or retention are disabled. [Shopify's 2026 explanation](https://help.shopify.com/en/partners/help-support/faq/ppa)

## Negotiated price settlement: supported options and remaining proof

### Option A — invoice checkout, recommended for the constrained first release

The Admin API documents draft orders for sales through chat, discounted/wholesale prices and secure checkout links. `draftOrderCreate` requires `write_draft_orders` (or the specialized quick-sale scope) and draft-order permission; its reference does not state a Shopify Plus restriction for ordinary draft creation. This supports feasibility on ordinary stores, subject to an actual representative-store installation/test. [Create draft](https://shopify.dev/docs/api/admin-graphql/latest/mutations/draftOrderCreate)

Use real `variantId` and quantity plus explicit `priceOverride` in the draft's presentment currency. Unlike custom-item original price fields, price overrides replace the variant catalog price while retaining the variant reference. Overrides cannot apply to bundle components and are removed if a line becomes part of a bundle. [Line input](https://shopify.dev/docs/api/admin-graphql/latest/input-objects/DraftOrderLineItemInput)

Set `acceptAutomaticDiscounts` and `allowDiscountCodesInCheckout` false, omit additional discount codes and avoid overlapping order/line discounts. These are documented controls; verify the actual checkout respects the agreed merchandise subtotal and the no-stacking policy. `reserveInventoryUntil` reserves inventory only. No quote-expiry field is listed on `DraftOrderInput`. [Draft input](https://shopify.dev/docs/api/admin-graphql/latest/input-objects/DraftOrderInput)

**Proposed safeguards:** server rechecks cost, floor, catalog availability and current pause state; server allocates exact integer minor-unit line prices and audits their sum; create one draft per accepted offer using durable idempotency; return Shopify's `invoiceUrl`; reject unsupported currencies, selling plans and transformed bundles before presenting an offer. Ordinary bundles assembled by Dealify from separate untransformed variants are different from Shopify bundle components. If a cart total cannot be represented by equal per-unit prices, use a tested allocation strategy rather than rounding away a cent. These are proposed design constraints, not claims of existing implementation.

Invoice checkout allows the shopper to enter billing details, choose shipping and pay. Consequently, the offer should describe **merchandise subtotal**, with tax/shipping resolved at checkout; never promise the complete final charge without calculating those components. Do not call `draftOrderComplete` merely because a shopper accepts an offer. [Invoice behavior](https://help.shopify.com/en/manual/fulfillment/managing-orders/create-orders/send-draft)

**Expiry and revocation are not proven by using drafts.** Shopify explicitly states that updating a draft after invoice checkout begins unlinks that checkout and does not stop its checkout/order creation; the draft can remain open even after an order is created. Therefore, repricing or updating the draft is not reliable revocation. [Update semantics](https://shopify.dev/docs/api/admin-graphql/latest/mutations/draftOrderUpdate)

`draftOrderDelete` deletes a draft, but its documentation does not guarantee cancellation of an already-open checkout. Deleting a completed draft does not delete its resulting order. Do not claim either a timer in the widget or deletion alone enforces strict expiry everywhere. [Delete API](https://shopify.dev/docs/api/admin-graphql/latest/mutations/draftOrderDelete), [Deletion behavior](https://help.shopify.com/en/manual/fulfillment/managing-orders/create-orders/create-draft)

**Release decision:** for an invoice pilot, define the timer as a deadline to accept the quote and issue checkout; disclose that an issued Shopify checkout may remain available, if that is the verified behavior. If exact checkout expiry or immediate post-mint PAUSE revocation is a product invariant, this remains a release blocker until a supported mechanism is proven. Avoid modifying an issued draft; keep a durable record and reconciliation state. Cleanup of abandoned drafts is hygiene, not a proven transaction lock.

**Attribution:** persist `shop ID → offer ID → draft ID`. `DraftOrder.order` is the documented resulting-order link. Additionally carry a non-secret application reference in supported metadata and verify its persistence in an actual paid order; it is a correlation hint, not authorization. Detect unknown/changed references rather than crediting revenue blindly. `sourceName` requires a configured sales-channel attribution handle, so do not invent `sourceName: dealify` for a regular app. [Draft order](https://shopify.dev/docs/api/admin-graphql/latest/objects/DraftOrder), [Source field](https://shopify.dev/docs/api/admin-graphql/latest/input-objects/DraftOrderInput)

**Required practical proof for this architecture:** on a development store with a test payment provider, record the draft response, checkout and resulting paid order for: two variants with unequal quantities; rounding; tax and shipping; an existing cart; catalog price changes after issue; disabled automatic/code discounts; repeated accept requests; multiple invoice opens; expired-before-accept requests; process restart; unavailable inventory; merchant-edited draft; and unsupported bundle/selling-plan rejection. Also determine what happens when an issued draft is deleted before opening and after checkout is already open. These are controlled functional tests, not evidence already obtained or exploit testing.

### Option B — native cart with a Discount Function

Public apps distributed through the App Store can use Functions on all plans, subject to each API's exceptions. Custom apps containing Functions are limited to Shopify Plus. That makes an unreviewed custom-app pilot on a normal plan a poor way to validate a Function-based public release. [Function availability](https://shopify.dev/docs/api/functions/latest)

Discount Functions receive cart lines/quantities/merchandise and discount metafield configuration, and can return fixed-amount product discounts. Function execution can therefore evaluate the final cart before returning the negotiated discount. This is a supported building block, not proof that an arbitrary implementation preserves every pricing invariant. [Discount Function schema and examples](https://shopify.dev/docs/api/functions/latest/discount)

**Proposed design:** mint a unique app-code discount whose server-written app-owned configuration contains the expected variant/quantity multiset, supported currency and line-level discount amounts. The Function returns no discount unless the final cart matches the entire expected deal. Never accept a discount amount from shopper-editable cart attributes. Use `discountCodeAppCreate`, native expiry/usage limits and non-combination settings; select customer eligibility only when authenticated buyer binding is a deliberate supported feature. A random guest code is a bearer benefit, not verified identity. [Create app discount](https://shopify.dev/docs/api/admin-graphql/latest/mutations/discountCodeAppCreate), [Code input controls](https://shopify.dev/docs/api/admin-graphql/latest/input-objects/DiscountCodeAppInput)

Do not make checkout depend on calling Dealify/Backboard over the network: Discount Function network access is currently an Enterprise/custom-app capability requiring enablement. Use Shopify-resident input/configuration. [Network restrictions and alternatives](https://shopify.dev/docs/apps/build/functions/network-access)

**Decision:** this option better fits a regular mutable-cart journey and native discount lifetime. It adds a Function build/release/test dependency and exact-cart rule design. Invoice checkout is the smaller first-release surface only if its quote/checkout lifetime semantics are accepted and demonstrated. Neither route should advertise an absolute margin guarantee against all merchant-side edits, taxes, refunds, transforms or later product changes.

## Data, AI and consent decisions for the free release

**Protected-data scope:** orders, draft orders, refunds and related webhooks are protected customer data even when names, email, address and phone are absent. Level 1 access requires request/review; requesting the identifying fields adds level 2 requirements. Development-store access does not prove public-store approval. Minimize API fields and design around omitted/redacted data. [Protected-data rules](https://shopify.dev/docs/apps/launch/protected-customer-data)

**Recommendation:** ship session-only negotiation first. Avoid collecting shipping/contact/payment details in chat; let Shopify checkout collect them. Disable persistent personalization until its opt-in/out and deletion are verified. Do not silently initialize persistent identity or provider memory merely from viewing a product page.

Shopify's Customer Privacy API exposes purpose-specific permissions for preferences, analytics, marketing and data sharing, plus consent-change events. Persistent size/preference memory fits the API's preference examples; interaction analytics has a separate permission. Purpose classification and the legal basis for a requested conversational service require actual policy decisions; a cookie banner does not automatically authorize every downstream AI use. [Privacy API](https://shopify.dev/docs/api/customer-privacy)

**Provider checklist to complete before release (recommended evidence):** identify Backboard, model provider, Supabase, hosting, logging and any voice processor; inventory sent fields and stored artifacts; verify contractual training restrictions, retention, deletion/export APIs and region/transfers; test deletion using disposable data; retain a deletion-job audit without preserving deleted content. Do not promise a processor property that has not been verified in that account/contract.

Shopify's API terms restrict using API/merchant/customer data—including derived data—to create, train, fine-tune or improve AI systems without the specified consent exception. They also limit onward transfers and require appropriate deletion and access/export behavior. Inference for an authorized merchant feature must not quietly become shared-model training. [API terms, updated October 7, 2026](https://www.shopify.com/legal/api-terms)

All three privacy webhooks apply even if the app claims to collect no personal data. A valid request must be acknowledged and the requested action completed within 30 days, subject to legally required retention. `shop/redact` arrives about 48 hours after uninstall. A 200 response without an export/deletion job is not completion. [Compliance webhooks](https://shopify.dev/docs/apps/build/compliance/privacy-law-compliance)

Recommended merchant-visible deliverables: policy/DPA, concise AI disclosure, exported conversation/deal data, deletion workflow and retention explanation. Keep legal/business claims out of placeholder copy until the operator confirms them. [Policy requirements](https://shopify.dev/docs/apps/launch/privacy-requirements)

## Minimum scope proposal

This is a proposal to reconcile against actual calls, not permission to request everything preemptively. Shopify access scopes are resource-specific; write scopes include corresponding read access. `read_orders` normally covers the latest 60 days; `read_all_orders` requires separate approval and is unnecessary for a new pilot that starts measuring its own sales now. [Scope catalog](https://shopify.dev/docs/api/usage/access-scopes)

| Scope | Proposed use | Decision |
|---|---|---|
| `read_products` | Catalog/variant identity and retail pricing | Retain if the implementation reads these resources. |
| `read_inventory` | Stock and cost inputs | Retain for the existing inventory/cost queries; validate actual field permissions. |
| `write_draft_orders` | Invoice creation, retrieval and cleanup | Needed for chosen draft route; also justify protected customer data. |
| `read_orders` | Paid order/refund/cancellation reconciliation | Retain only with implemented reporting/reconciliation. |
| `write_discounts` | Native/Function discount minting and deactivation | Omit in a draft-only release unless a shipped feature still uses it. |
| `write_products` | Product/metafield writes | Omit if the new release only reads catalog/cost and stores policy in its own database. |
| `write_app_proxy` | Shopify app-proxy route configuration | Request only if the implemented proxy/configuration requires it. |
| `read_all_orders`, customer write scopes, payment mandates, checkout chat/pixel scopes | No initial supported feature | Exclude. Storefront chat is not a checkout chat extension. |

## Free pilot, listing and review package

A truly free app need not create charges. When charges are introduced, use Shopify billing; the recommended new-app path is Shopify App Pricing, whose plans live in the Partner Dashboard and whose subscriptions follow merchant plan approval. Do not integrate external merchant subscription checkout for app fees. [Billing requirements](https://shopify.dev/docs/apps/launch/shopify-app-store/app-store-requirements), [Shopify App Pricing](https://shopify.dev/docs/apps/launch/billing/shopify-app-pricing)

**Recommendation:** label the release free with explicit included limits and an honest pilot policy; do not require future billing authorization. If pricing later changes, give advance notice and obtain required Shopify plan approval; decide and document whether pilot merchants keep a free plan. Shopify's 2026 partner clarification specifically addresses advance pricing-change notice. [Pricing transparency](https://help.shopify.com/en/partners/help-support/faq/ppa)

Public distribution requires review and an App Store listing. Limited visibility removes search/category discoverability but still installs through a listing URL and follows the same review rules. A free pilot does not bypass approval for unrelated production stores. Use development stores before approval; if a separate one-merchant custom registration is used, document its distribution/Function/IP limitations and later reinstall migration rather than treating it as the same app identity. [Visibility](https://shopify.dev/docs/apps/launch/distribution/visibility), [Review process](https://shopify.dev/docs/apps/launch/app-store-review/review-process), [Distribution choice](https://shopify.dev/docs/apps/launch/distribution/select-distribution-method)

Recommended submission package:

1. A named stable release, supported-store eligibility and exact feature limitations.
2. A plain benefit statement, truthful feature descriptions and consistent Dealify naming.
3. Actual desktop/mobile widget and Console screenshots; a 1200×1200 icon and 1600×900 screenshots are the current listing guidance.
4. A dedicated privacy URL, support contact and setup/help pages; emergency developer contact in the Partner account.
5. An English screencast: Shopify install → authenticated Console → configure floor/cost → enable embed → negotiate → issued invoice → test payment → verified ledger → pause/uninstall/reinstall.
6. A reviewer recipe with products/costs, expected quote and outcome, required credentials, representative errors, and AI fallback behavior. Keep dedicated credentials usable without interactive external authentication.
7. Completed automated checks and protected-data request, plus live test evidence for the active release.

The asset dimensions and practical listing advice above come from Shopify's listing guidance; the screencast/credential obligations come from the requirements. Avoid unsupported results guarantees or calling an unfinished beta production-ready. [Listing guidance](https://shopify.dev/docs/apps/launch/shopify-app-store/best-practices), [Submission requirements](https://shopify.dev/docs/apps/launch/shopify-app-store/app-store-requirements), [Submission readiness](https://shopify.dev/docs/apps/launch/app-store-review/submit-app-for-review)

App configuration/extensions release as Shopify app versions; deploying one does not deploy the web backend. Verify both deployments and their compatibility. Release/production configuration should not point to a development tunnel. [Deploy app versions](https://shopify.dev/docs/apps/launch/deployment/deploy-app-versions)

## App Store baseline versus Built for Shopify

Built for Shopify is a separate quality qualification; do not treat every BFS metric as an initial App Store approval condition. BFS includes assessed merchant-use/review signals and admin Web Vitals targets: p75 LCP ≤2.5s, CLS ≤0.1, INP ≤200ms, with at least 100 observations per metric over 28 days. Its embedded-workflow/design requirements are additional qualification criteria. [BFS requirements](https://shopify.dev/docs/apps/launch/built-for-shopify/requirements)

The ≤10-point storefront Lighthouse impact is **also an App Store publication requirement**, not merely a BFS target. Shopify's documented test uses home/product/collection weights of 17%/40%/43%. Compare the same clean theme/store with the widget disabled and enabled and average repeated mobile tests. [Publication performance](https://shopify.dev/docs/apps/build/performance), [Measurement method](https://shopify.dev/docs/apps/build/performance/storefront)

Recommendation: meet the approval baseline now; adopt small assets, deferred chat loading, accessible controls and standard admin navigation immediately because they reduce merchant problems, then pursue BFS once there is enough real usage to assess it.
